    피드백으로 갈고닦기 — 기획서 최종 완성¶

    Part 4. 완성 — 기획서를 쓰고, 발표하고, 제출하다 | 11차시 (50분)

    🎯 이 장에서 배우는 것¶

    • 다른 팀의 기획서를 심사 기준(루브릭)에 따라 구조적으로 피드백할 수 있다
    • 받은 피드백을 수용·보류·반려로 분류하고 수정 계획을 세울 수 있다
    • 최종 체크리스트를 활용하여 기획서 최종본을 완성할 수 있다

    📚 핵심 개념¶

    개념 1: 구조적 피드백 (Structured Feedback)¶

    1. 비유로 시작

    💡 구조적 피드백은 마치 건강검진표와 같아요. 의사가 "어딘가 안 좋아 보여요"라고 말하면 막막하지만, "혈압이 정상 범위보다 10 높으니 운동량을 늘려보세요"라고 말하면 바로 행동할 수 있죠. 기획서 피드백도 마찬가지입니다.

    2. 정확한 정의

    구조적 피드백이란, 정해진 기준(루브릭)에 따라 구체적인 근거와 개선 방향을 함께 제시하는 피드백 방식입니다. "좋다/나쁘다" 같은 느낌이 아니라, 어디가·왜·어떻게를 담아야 합니다.

    3. 예시로 확인

    • ❌ 비효과적: "데이터 부분이 좀 약한 것 같아요"
    • ✅ 효과적: "3페이지 그래프의 출처가 빠져 있어요. 통계청 원자료 링크를 추가하면 신뢰도가 높아질 것 같습니다"

    🔍 알아보기: 효과적인 피드백의 3요소 - 위치 — 몇 페이지, 어떤 문장인지 콕 집기 - 근거 — 왜 문제인지 이유 설명하기 - 제안 — 구체적인 개선 방법 제시하기

    개념 2: 피드백 분류법 (수용·보류·반려)¶

    1. 비유로 시작

    💡 피드백을 받는 것은 마치 택배 상자를 여는 것과 같아요. 주문한 물건(타당한 지적)은 바로 꺼내 쓰고, 잘못 온 물건(우리 기획 방향과 다른 의견)은 반송하고, 확인이 필요한 물건(추가 조사가 필요한 제안)은 잠시 보관하죠.

    2. 정확한 정의

    받은 피드백을 세 가지로 나누는 의사결정 방법입니다.

    • 수용 🟢 — 타당하므로 바로 반영한다
    • 보류 🟡 — 일리 있지만, 추가 논의나 조사가 필요하다
    • 반려 🔴 — 우리 기획 의도와 맞지 않아 반영하지 않는다 (단, 이유를 기록)

    3. 예시로 확인

    피드백: "타겟 사용자를 초등학생에서 중학생으로 바꾸면 어떨까요?"

    • 🟢 수용: 실제로 설문 데이터가 중학생 응답이 더 많았다면
    • 🟡 보류: 데이터를 다시 확인해봐야 판단 가능하다면
    • 🔴 반려: 처음부터 초등학생 대상으로 문제를 정의했고 근거가 충분하다면

    💬 생각해보기: 반려한다고 해서 "틀린 피드백"은 아닙니다. 왜 반려했는지 이유를 기록하는 것이 핵심입니다. 이유 없는 반려는 그냥 무시이고, 이유 있는 반려는 팀의 판단력을 보여줍니다.

    🔨 따라하기: 피드백 세션 5단계¶

    Step 1: 피드백 루브릭 확인하기¶

    기획서를 읽기 전, 다음 5가지 평가 기준을 먼저 숙지합니다.

    [피드백 루브릭 5개 항목]

① 문제 명확성 — 해결할 문제가 구체적으로 정의되었는가?
② 데이터 활용도 — 주장을 뒷받침하는 데이터가 충분한가?
③ AI 적합성 — AI가 이 문제에 적합한 해결 수단인가?
④ 실현 가능성 — 시간·비용·기술 측면에서 현실적인가?
⑤ 발표 자료 완성도 — 슬라이드 구성, 가독성이 적절한가?

    각 항목을 상(3점)·중(2점)·하(1점)으로 평가하되, 반드시 한 줄 이상 개선 제안을 적어야 합니다.

    Step 2: 다른 팀 기획서 읽고 피드백 작성하기¶

    포스트잇(또는 메모장)에 다음 형식으로 작성합니다.

    [피드백 작성 형식]

📍 위치: ○페이지 / ○번째 문단(또는 슬라이드 번호)
📋 항목: (루브릭 5개 중 해당 항목)
💬 내용: (구체적 지적 + 개선 제안)

--- 예시 ---
📍 위치: 5페이지, 기대효과 슬라이드
📋 항목: ② 데이터 활용도
💬 내용: "학생 70%가 어려움을 느낀다"는 수치의 출처가 없습니다. 
   설문 결과라면 응답자 수와 조사 시기를 추가해주세요.

    Step 3: 받은 피드백을 수용·보류·반려로 분류하기¶

    팀원이 함께 모여 받은 피드백을 하나씩 읽으며 분류합니다.

    # 피드백 분류를 정리하는 간단한 코드
feedbacks = [
    {"내용": "5페이지 데이터 출처 누락", "분류": "수용", "조치": "통계청 링크 추가"},
    {"내용": "타겟을 중학생으로 변경 제안", "분류": "반려", "이유": "초등학생 대상 설문 근거 충분"},
    {"내용": "AI 모델 비용 추정 필요", "분류": "보류", "조치": "API 가격 조사 후 결정"},
]

for i, fb in enumerate(feedbacks, 1):
    status = {"수용": "🟢", "보류": "🟡", "반려": "🔴"}
    print(f"{i}. {status[fb['분류']]} [{fb['분류']}] {fb['내용']}")

    실행 결과: 

    1. 🟢 [수용] 5페이지 데이터 출처 누락
2. 🔴 [반려] 타겟을 중학생으로 변경 제안
3. 🟡 [보류] AI 모델 비용 추정 필요

    Step 4: 수용 항목 반영하여 기획서 수정하기¶

    분류 결과 중 🟢 수용 항목을 우선 반영합니다. 수정 전후를 기록해두면 나중에 개선 과정을 설명할 수 있습니다.

    # Before-After 기록 예시
revisions = {
    "5페이지 기대효과": {
        "before": "학생 70%가 어려움을 느낀다.",
        "after": "학생 70%가 어려움을 느낀다. (출처: 2024 교육부 실태조사, 응답자 1,200명)"
    }
}

for page, change in revisions.items():
    print(f"📄 {page}")
    print(f"  ❌ 수정 전: {change['before']}")
    print(f"  ✅ 수정 후: {change['after']}")
    print()

    실행 결과: 

    📄 5페이지 기대효과
  ❌ 수정 전: 학생 70%가 어려움을 느낀다.
  ✅ 수정 후: 학생 70%가 어려움을 느낀다. (출처: 2024 교육부 실태조사, 응답자 1,200명)

    Step 5: 최종 체크리스트로 마무리하기¶

    제출 전 반드시 확인해야 할 항목들입니다.

    # 최종 체크리스트 점검 도구
checklist = {
    "오탈자 검수 완료": True,
    "모든 데이터에 출처 표기": True,
    "슬라이드 번호 삽입": False,  # 아직 안 했다면!
    "파일명 규칙 준수 (팀명_기획서_v최종)": True,
    "PDF 변환 확인": False,
}

print("📋 최종 체크리스트")
print("=" * 40)
all_done = True
for item, done in checklist.items():
    mark = "✅" if done else "⬜"
    if not done:
        all_done = False
    print(f"  {mark} {item}")

print()
if all_done:
    print("🎉 제출 준비 완료!")
else:
    print("⚠️ 미완료 항목이 있습니다. 확인 후 제출하세요!")

    실행 결과: 

    📋 최종 체크리스트
========================================
  ✅ 오탈자 검수 완료
  ✅ 모든 데이터에 출처 표기
  ⬜ 슬라이드 번호 삽입
  ✅ 파일명 규칙 준수 (팀명_기획서_v최종)
  ⬜ PDF 변환 확인

⚠️ 미완료 항목이 있습니다. 확인 후 제출하세요!

    📝 전체 흐름 정리¶

    flowchart LR A["1️⃣ 루브릭 확인"] --> B["2️⃣ 피드백 작성"] B --> C["3️⃣ 분류\n수용·보류·반려"] C --> D["4️⃣ 수용 항목\n기획서 반영"] D --> E["5️⃣ 최종 체크리스트\n점검 & 제출"]

    ⚠️ 주의할 점¶

    1. 피드백은 '사람'이 아니라 '기획서'에 하는 것입니다

    "너희 팀은 준비를 안 한 것 같아"가 아니라, "3페이지 문제 정의 부분에 구체적인 사례가 추가되면 더 설득력이 있을 것 같습니다"처럼 문서의 특정 부분에 대해 이야기하세요.

    2. 반려할 때 반드시 이유를 남기세요

    이유 없이 무시하면 같은 피드백을 발표 심사에서 다시 받을 수 있습니다. "우리가 이 부분을 왜 이렇게 결정했는지" 기록해두면, 발표 때 질의응답에서도 자신 있게 답할 수 있습니다.

    ✅ 점검하기¶

    기본 문제: 다음 중 구조적 피드백의 3요소를 모두 갖춘 문장은?

    • (가) "전체적으로 괜찮은 것 같아요."
    • (나) "4페이지 그래프 색상이 두 개 겹쳐서 구분이 어려워요. 색상을 파랑/주황으로 바꾸면 좋겠습니다."
    • (다) "데이터가 부족해요."
    정답 확인 **(나)**가 정답입니다. - **위치**: 4페이지 그래프 - **근거**: 색상이 겹쳐서 구분이 어렵다 - **제안**: 파랑/주황으로 변경 (가)는 위치·근거·제안이 모두 없고, (다)는 위치와 제안이 없습니다.

    응용 문제: 피드백 "AI 대신 단순 규칙 기반으로도 충분할 것 같은데, AI를 꼭 써야 하는 이유가 기획서에 안 보여요"를 받았습니다. 이 피드백을 수용한다면 기획서 어느 부분을 어떻게 수정해야 할까요?

    정답 확인 **'AI 적합성' 또는 'AI 솔루션 소개' 섹션**에 "규칙 기반 방식과 AI 방식의 차이점"을 비교하는 내용을 추가합니다. 예시: *"단순 규칙 기반은 ○○ 상황에서 정확도가 60%에 그치지만, AI 모델은 패턴 학습을 통해 85%까지 높일 수 있다"*와 같이 AI가 더 나은 근거를 데이터로 보여주면 됩니다.

    심화 문제 (도전!): 피드백 반영 전후의 슬라이드를 Before-After로 캡처한다고 가정합니다. 왜 Before-After 기록이 중요한지 두 가지 이유를 적어보세요.

    정답 확인 1. **성장 과정 증명**: 심사위원에게 "피드백을 수용하고 개선할 수 있는 팀"이라는 인상을 줄 수 있습니다. 2. **의사결정 근거 보존**: 나중에 "왜 이렇게 바꿨지?"라는 질문에 명확히 답할 수 있고, 되돌려야 할 때 이전 버전을 참고할 수 있습니다.

    📌 정리하기: 이 장의 핵심 - 좋은 피드백은 위치 + 근거 + 제안 세 가지를 모두 갖춘다 - 받은 피드백은 수용 🟢 · 보류 🟡 · 반려 🔴로 분류하고 이유를 기록한다 - 제출 전 최종 체크리스트(오탈자, 출처, 슬라이드 번호, 파일명, PDF 변환)를 반드시 점검한다

    드디어 마지막 차시입니다! 완성된 기획서를 바탕으로 발표를 실행하고, 심사위원(또는 동료)의 질의응답에 대응하는 방법을 배웁니다. 발표가 끝난 뒤에는 프로젝트 전체를 회고하며, 이 과정에서 무엇을 배웠고 다음에 무엇을 더 잘할 수 있을지 정리합니다. 🎤✨
